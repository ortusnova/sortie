# This fork

This repository is the agentic-orchestration fork of [Sortie](https://github.com/sortie-ai/sortie). Its working branch is `plan-bench`; agentic-orchestration pins it as the `sortie/` submodule.

## Merging upstream

- Merge upstream `main` into `plan-bench` at each upstream release, or weekly when no release comes, whichever is sooner.
- Merge, never rebase: open a `merge/upstream-<date>` branch from `plan-bench`, run `git merge upstream/main`, and land it through a pull request. Rebasing would rewrite commits that agentic-orchestration's submodule pins.
- Record in the merge commit body each conflict whose resolution changed the meaning of either side: the file, what each side did, and what was kept. Record the upstream commit merged, so the next merge knows where it starts.
- Keep fork work in fork-owned packages and files, with small hooks in upstream files, so each merge stays small. Fork database migrations are numbered from 1001 and fork ADRs from 1001, so upstream's numbers never collide with them.

Last merged upstream commit: `c48b724b` (2026-10-28).

## Worker leases

Jobs for `environment.kind: remote` are matched to workers in `internal/worker`, wired into the orchestrator in `internal/orchestrator/remote.go`, configured in `internal/config/environment_remote.go` and served by `internal/server/worker.go`, following the `agent-platform/worker-api` (protocol 1) and `agent-platform/worker-dispatch` specs. The lease rule sits behind the `worker.Leaser` interface. Until upstream #1499 settles, the fork follows a fixed-duration rule (`TTLLeaser`): one worker holds a job at a time, a lease lasts its TTL from the grant or last renewal, and an expired lease ends the attempt as failed; the worker's run slot, CPUs and memory return, and its disk stays counted as a stopped machine's until the worker's next check-in. Replacing the rule means implementing `Leaser`. Placement is `place` in `internal/worker/worker.go`, which both `Matcher.Poll` and `Matcher.Placeable` use: jobs fewer workers are capable of are placed first, and each job goes to the worker it fits with the fewest capabilities it does not need, then to the polling worker, so a scarce capability such as `nested` is spent only on the jobs that need it; a poll offers a worker only the jobs placed on it.

## Remote runs

A remote attempt is a normal worker run (`RunRemoteAttempt` in `internal/orchestrator/remote.go`, following `agent-platform/remote-runs`): the attempt's execution environment is the job's machine, Sortie drives the agent session over the `stdio` flow through `sortie stdio-bridge`, and seeds and pushes the repository through `internal/gitsync` (`BuildSeed`, `ImportReturned`). `internal/dataplane` serves the `stdio`, `mcp`, `bundles` and `usage` flows under `/api/v1/flows/`, each request admitted by its flow's job token. The remote attempt is a tool-channel environment whose host socket is the data plane's: the session's tool server is served there as for a VM, and the `mcp` flow forwards each admitted request to it with the bearer the channel's `Authorize` hook hands it, so a tool call acts on its own job's session. No forge credential reaches a worker.

## A restart keeps the remote runs

A Sortie restart interrupts no remote run, following `agent-platform/run-supervision` ("A Sortie restart interrupts no run, and a deploy never drains"). From a worker's lease grant to the attempt's end, `internal/orchestrator/remote.go` keeps the run's record in `remote_runs` (migration 1011, `internal/persistence/remote_runs.go`): the job, the worker, the job tokens' digests (`jobtoken.Issuer.Digests`) and the seed at the grant (`worker.Matcher.Granted`), the agent session and its turns from the adapter wrapper, and the running entry (issue, dispatch, attempt, stage, reaction, budgets, broker) from the event loop. At shutdown the attempt is left with its worker: once the event loop's context ends, a recorded attempt never cancels its job, deletes its record or sends the `C` frame (`dataplane.Options.Keep`, `Attempt.Detach`), and its exit records nothing (`keepRemoteExit`). At start, `RestoreRemoteRuns` restores the leases (`worker.Matcher.Adopt`) and tokens (`jobtoken.Issuer.Restore`) before the server serves the worker API, and `adoptRemoteRuns` puts each run back in the running map with its dispatch ID and starts its worker with `RunRemoteAttempt`'s `Adopt`: the session resumes the recorded one and the turns continue after the completed ones (`WorkerDeps.Adopted`). The code is in `internal/orchestrator/remote_adopt.go`. Hooks in upstream files: `WorkerDeps.Adopted` and its three checks in `RunWorkerAttempt` (no in-progress transition, no `session.started`, the turn counters and skip), the `keepRemoteExit` check in `handleWorkerExit` and `drainRunningWorkers`, `detachRemoteRuns` in `drainRunningWorkers`, `adoptRemoteRuns` in `Run`, the record after a broker report in `handleControl`, the store in `NewOrchestrator`, the two `RemoteAttemptParams` in `makeWorkerFn`, and `RestoreRemoteRuns` in `cmd/sortie/main.go`. The worker side is worker-daemon's: on a broken stream it keeps the job's machine, dials the `stdio` flow again and starts the agent again. A CI log excerpt is never stored, so a CI fix turn run again after a restart has an empty one.

## Failure causes

A failed run keeps its whole cause in `run_history.error_detail` (migration 1005), served as `error_detail` on every run row, following `agent-platform/run-supervision`. `internal/failcause` reads it from the first error in the run error's chain that has a `FailureOutput() string` method, masks it and caps it; `gitsync.Error` (a git command's porcelain output and standard error) and the `agent-client-protocol` adapter's JSON-RPC error cause (the runtime's error object) have one. Another adapter adds a cause by giving its error that method.

A run that ends on an error also gets a failure signature in `run_history.failure_signature` (migration 1006), following the requirement "The same failure twice stops the retries" of `agent-platform/run-supervision`. `failcause.Sign` builds it from the failed step the orchestrator names, the class `failcause.Classify` gives the error, and the error's first line through `failcause.Normalize`. An error type names its own class with a `FailureClass() string` method, as `gitsync.Error` does (`git_<subcommand>`). When an issue's run fails with the signature of its previous run and the class is not transient, the exit parks the issue with the reason `repeated_failure` instead of scheduling a retry; the transient classes are listed in `failcause.TransientClasses`.

A repeated failure is then routed by its fault class, following the requirement "A stopped failure goes to whoever can act on it" of `agent-platform/run-supervision`. `failcause.RouteOf` matches the signature against `failcause.FaultClasses`, a fixed, ordered list of story and platform classes with the signature patterns in each and, for a platform fault only a person can clear, the action template. A story fault schedules one retry with the trigger `story_fault` whose first-turn prompt gets the failure section (`prompt.FailureHandOver`); its own repeat parks the issue with `repeated_failure`. A platform fault is recorded once in `platform_faults` (migration 1009, `internal/orchestrator/platform_fault.go`) and holds its stories in `State.FaultHolds`, which the dispatch gates and the retry timer respect. `internal/orchestrator/platform_fault_check.go` runs the checks: on the poll tick when due, every `PlatformFaultCheckInterval`, and at once from `POST /api/v1/platform-faults/{id}/action-done` (`internal/server/platform_fault.go`). The default check probes an `export` fault with `gitsync.Syncer.PushIncoming`, and otherwise passes a person-action fault once it is marked done. The workbench reads `platform_faults` on `/api/v1/state` and asks each `person_action` as a question naming its stories; marking the question done calls the action-done route. The host a person action names is the machine's host name.

## Plan sync from the workbench

The agentic-orchestration workbench syncs the plan on its own, with no Sync step for the user. It calls `POST /api/v1/plan/sync` with `"apply": false` to preview, then applies that preview with `"apply": true` and the preview's `preview_id`. After a sync that released a story, it calls `POST /api/v1/refresh` so the released story is dispatched on the next tick instead of the next poll. Both routes take the control token. Nothing else in Sortie changes for this.

## Draining a host

The stage-0 kit drains a host before a deploy or a host setup change, following `agent-platform/run-supervision` ("A pending deploy drains its host"). It calls `POST /api/v1/dispatch/pause`, waits until `running` on `/api/v1/state` is empty, applies the change, and calls `POST /api/v1/dispatch/resume`; both routes take the control token. The pause lives in `internal/orchestrator/dispatch_pause.go` and `internal/server/dispatch_pause.go`, with one hook in the poll tick's dispatch pass and one in `HandleRetryTimer`. It is kept in memory, so a restart clears it: the kit resumes after every change and repeats its pause each minute while it waits, so a persisted pause would add nothing and could leave a host paused with no one to resume it.

Under `environment.kind: remote` a restart keeps the runs its workers hold (see below), so a deploy of such a Sortie needs no drain.

## More sessions for one issue

The workbench unblocks a story the session budget holds, following `agent-platform/run-supervision` ("Unblock from the lane"). It calls `POST /api/v1/{identifier}/sessions` with `{"add": N, "by", "reason"}` and the control token, and the issue runs again without a change to `agent.max_sessions` for every issue. The grant lives in `internal/orchestrator/session_grant.go`, `internal/server/session_grant.go` and `internal/persistence/session_grants.go` (table `session_grants`, migration 1007). Hooks in upstream files count it: the poll tick's budget set in `rebuildBudgetExhausted`, the session gate in `HandleRetryTimer`, the snapshot, the served rows and sentences, and the `cost_budget` tool. Grants are stored, unlike the dispatch pause, because a story granted sessions must not be held again by a restart.

## The supervisor token

An agent supervises runs through a token of its own, following `agent-platform/run-supervision` ("The supervisor acts only through a scoped API, and each action is recorded"); blockers that need a person still go to a person. `server.supervisor_token` is accepted only on the routes of its actions: `answer`, `sessions` (capped by `server.supervisor_max_sessions`), and the fork's `unpark`, `merge-record`, `fix`, `draft`, `merge`, `live-proof` and `POST /api/v1/issues`. Every other control route answers it `403`. The scope check is in `requireControl` (`internal/server/auth.go`, the `scopeSupervisor` scope); the routes, the evidence check and the record are in `internal/server/supervisor.go`, the actions in `internal/orchestrator/supervisor.go`, and the record in `internal/persistence/supervisor_actions.go` (table `supervisor_actions`, migration 1008). Hooks in upstream files: the two routes it shares with the operator, the cap on `SessionGrantRequest`, the `released` park gesture, the `supervisorView` member embedded in the state response and its `attachSupervisorActions` call, the `prDrafter` field, and the wiring in `cmd/sortie`. The draft capability is the optional `domain.PullRequestDrafter`, implemented by the GitHub adapter only. Sortie runs no live proof: a `live-proof` request is its stored record.

## Later turns of a reaction run

The fork changes the rule of upstream ADR 0037 for later turns. In `BuildReactionTurnPrompt` (`internal/prompt/reaction.go`), a turn after the first gets the operator's branch only when the branch renders differently with `.run.is_continuation` false; otherwise it gets the built-in continuation text, which also says that the earlier turns' commits are in the workspace and that `origin/<branch>` moves only after the run. Seen on 2026-11-02 and 03 in stage-0 fix runs (ONS-50, ONS-51, ONS-55, ONS-83): the fix template had no continuation branch, so each later turn asked again for the merge the agent had already committed, and the agent, seeing `origin/<branch>` unchanged because Sortie pushes after the run, parked to ask why Sortie did not push. The seed and refresh were correct: the next run's refresh moved `origin/<branch>` to the pushed commit.

## What each worker does

The workbench shows each worker host, its jobs and what waits on it, following `agent-platform/run-supervision` ("The workbench shows what each worker is doing and what waits on it"). `GET /api/v1/state` serves `host`, `waits`, `pulls`, and on each running row `worker`, `phase`, `step`, `step_at` and `estimated_end`, built in `internal/server/worker_view.go` from the snapshot, the worker matcher, run history and `internal/hostview`. `internal/hostview` reads the host's capacity and lists its machines through `smolvm machine ls --json` (`internal/environment/smolvm/inventory.go`), wired in `cmd/sortie/hostview.go`. The worker API carries a check-in's optional `used` and `unmanaged` and a heartbeat's optional step (`internal/worker/activity.go`). Hooks in upstream files: the `workerView` and `runningWorkerView` members embedded in the state and running responses, the `attachWorkerView` call in `handleState`, the `HostFn` parameter, and one line in `cmd/sortie/main.go`. Sortie knows no live proof, so it serves no `live_proof` wait or pull; a run outside `remote` reports no step.

A client draws each worker's past and forecasts where a queued job runs from two more members. Run history keeps the worker that held a remote run's lease in `run_history.worker` (migration 1013), served as `worker` on every run row: `remoteAttempt` takes it from `worker.Matcher.Granted`, or from the adopted run's record, and `adjust` sets `WorkerResult.Worker`, which the exit writes. `config.repositories[].requires` serves what the matcher requires of a worker for a job of each repository (`remoteRequires`, the backend among the capabilities), `null` outside `remote`. Hooks in upstream files: the `Worker` field of `WorkerResult`, `RunHistory`, `RunHistoryEntry` and the run response, one line in `HandleWorkerExit` and one in `cmd/sortie/runhistory.go`.

## smolvm egress with virtio-net

Answer: smolvm filters egress with `virtio-net`, and does not with TSI. Measured on smolvm 1.32.4 on 2026-11-01, on p1 (Intel, `kvm_intel nested=Y`), with throwaway Alpine 3.22 machines.

- **virtio-net filters.** A machine created with `--net-backend virtio-net --allow-host-pattern ghcr.io` reached `ghcr.io` (`HTTP/1.1 301`). `example.com` did not resolve (NXDOMAIN), `1.1.1.1` and `93.184.215.14` refused the connection, and `smolvm machine egress-events` recorded each refusal, including `github.com`, where the `ghcr.io` redirect points.
- **The default backend is the same.** Without `--net-backend`, a machine with an allowlist used the same virtio-net stack (`eth0`, resolver `100.96.0.1`) and showed the same results. So a workflow without `net_backend` keeps today's machines.
- **TSI does not filter.** smolvm refuses to create a machine with `--net-backend tsi` and any egress policy: "egress policy ... requires the virtio-net backend; TSI does not enforce it". A TSI machine has no `eth0` and uses the host's resolver.
- **A backend needs a network.** `--net-backend virtio-net` without an allowlist or a credential is refused: "--net-backend virtio-net requires --net". `--net` would open the network unfiltered.
- **Credentials need the allowlist.** A credential binding alone opens the network unfiltered, on every backend. With an allowlist that lacks the credential's host, smolvm refuses the machine. With the credential's host on the allowlist, which Sortie always adds, substitution works the same with virtio-net as without it.

So validation follows: `environment.smolvm.net_backend` accepts only `virtio-net`, refuses `tsi` and every other value, and refuses `virtio-net` without `allow_hosts` or `credentials`, each with an error on `environment.smolvm.net_backend`. Sortie never adds `--net`. The gated test `TestIntegration_NetBackendKeepsTheAllowlist` in `internal/environment/smolvm` checks the allowlist on a KVM host.

The same run measured the other host inputs. `--nested` gives the guest `/dev/kvm`, and `KVM_CREATE_VM` succeeds there; without it the guest has no `/dev/kvm`. `-v HOST:GUEST[:ro]` mounts over virtiofs: a read-only mount refuses every write, a link out of a mount does not reach the host, and smolvm accepts a mount under another one, such as under `/run/sortie/control`, so Sortie refuses that itself. A write to a mounted directory reaches the host at once, so it survives a `kill -9` of the machine, and `smolvm machine delete` leaves the directory alone.

## CI of a pull request in another repository

A workflow that dispatches several repositories (`dispatch.repositories`) has one CI provider, configured with one repository (`github.project`). Upstream's CI reaction read every pull request's CI from that repository, so a pull request in any other one got `422 No commit found for SHA` and its CI failure was never acted on. Seen live on p1 on 2026-11-03: `ortusnova/sortie#31` was read from `ortusnova/agentic-orchestration`. The providers now also implement `domain.RepositoryCIStatusProvider`, and the CI reaction reads each pull request's CI from the repository its reaction data names, with the same token (`internal/orchestrator/ci_reconcile.go`). The other pull request reactions already read the pull request's own repository through the SCM adapter.

## A queued reaction run across a restart

Upstream's merge-conflict reaction marked a conflicted head dispatched when it queued the rebase continuation, not when the run started. A queued continuation is runtime-only, so a restart loses it, and the mark kept the watch rebuilt at startup from dispatching that head again. Seen live on p1 on 2026-11-03: the merge-conflict reaction of `ortusnova/sortie#31` (ONS-78) queued its rebase at 04:05Z while every agent slot was busy, a deploy restarted Sortie at 08:12Z, and the pull request then stayed conflicted for hours with no rebase run. The fork drops that mark from `dispatchMergeConflictContinuation` (`internal/orchestrator/merge_conflict_reconcile.go`); `HandleRetryTimer` already marks the head when it starts the run, as it does for the `ci`, `review` and `bot-review` reactions. While the continuation waits, the retry-slot guard keeps the head from being queued twice. Persisting reaction retries instead was not chosen: their continuation context is not serializable as is, and the rest of the reaction state is rebuilt at startup, not stored.

Upstream's `label-review` and `label-fix` reactions likewise recorded a person's label command handled (the high-water mark, ADR-0015's at-most-once rule) and removed the command label when they queued the run, so a restart before the run started lost the command. The fork applies the same rule to them: the reconcile passes (`internal/orchestrator/label_review_reconcile.go`, `label_fix_reconcile.go`) queue the run with the command's mark and label on the retry entry (`RetryEntry.Command`), and `HandleRetryTimer` persists the mark and removes the label when it starts the run (`acknowledgeLabelCommand` in `retry.go`). While the run waits, the passes leave the mark alone, and the retry-slot guard keeps the command from being queued twice. A command whose run started is never repeated; a crash between the run starting and the mark write is the only window that can repeat one.

## The base branch in a remote run's workspace

Upstream's remote workspace seed bundled only `HEAD` and the issue branch. The worker daemon fetches every ref of the seed as it is (`+refs/*:refs/*`), so the workspace had no remote and no `origin/<base>`. Seen live on p1 on 2026-11-03: the merge-conflict runs of six stage-0 pull requests (ao#69, #79, #93 and sortie#51, #57, #58) each ran up to 20 turns of "there is no copy of `main` in this workspace to merge" and ended `succeeded` with nothing exported. `BuildSeed` (`internal/gitsync/seed.go`) now also bundles `refs/remotes/origin/<base>` and, when the upstream issue branch exists, `refs/remotes/origin/<issue branch>`, as a local workspace's refresh provides. `ImportReturned` now leases the push on the upstream commit the seed carried (`Seed.Upstream`) instead of on Sortie's last push: ONS-97's branch (ao#79) held a person's merge (`dbce406`) on top of Sortie's last push (`145162a`), so a returned merge on top of it would have been refused as `branch moved upstream`. A seed recorded before the upgrade has no `Upstream` and keeps the old lease.

## A rebase run that leaves the head unchanged

Upstream's merge-conflict reaction dispatched one rebase run per conflicting head. A run that ended with the head unchanged, because it could not merge, failed, or was lost to a restart after it started, left the head marked dispatched, and the pull request conflicted for good. Seen live on p1 on 2026-11-03: those pull requests, and ao#92 and ao#98, whose rebase runs a restart cancelled, stayed conflicting for hours after one run each, each with "0 of 1" attempts shown after a restart and no rebase run scheduled. The fork counts a head's dispatches in `reaction_fingerprints.dispatched` (`MarkReactionDispatched` adds one; the new `GetReactionDispatches` reads the count) and, in `handleMergeConflictDirty` (`internal/orchestrator/merge_conflict_reconcile.go`), gives a head still conflicting a poll interval after its runs ended, with no run of the issue running or queued, another run, up to `mergeConflictRunsPerHead` (3); then it escalates with the trigger `unresolved`. These runs spend no `max_retries` attempt, which keeps counting conflicting heads. A per-head bound in the store was chosen over the in-memory attempt counter, which a restart resets.

## CI with a fine-grained GitHub token

A GitHub fine-grained personal access token cannot read check runs: GitHub offers it no Checks permission, and `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` answers `403`. Seen live on taichi on 2026-11-03, where every pull request waited on `ci_auth_error`. When that endpoint refuses the token, the GitHub CI provider and the auto-merge CI gate read the GitHub Actions jobs of the head commit instead (`internal/scm/github/ci_actions.go`): the workflow runs for the commit, the newest run of each workflow and event, its latest-attempt jobs, and the failing job's log. The refusal is kept per repository for an hour. The hooks in upstream files are one call to `readCheckRuns` in `FetchRepositoryCIStatus` (`ci.go`) and one in `GetCIStatus` (`merge.go`), plus a `refusals` field on each of the two types. The token needs Actions read-only access beside Contents, Pull requests, and Commit statuses.

## A long tool call is not a stall

A run inside a tool call that is still in progress is not stalled while its worker shows the job alive. Upstream's stall check measures only the time since the last agent event, and a tool call emits none while it runs, so a long command ended at `agent.stall_timeout_ms`. Seen live on p1 on 2026-11-03: ONS-19 ran a seed step on taichi under `environment.kind: remote`, its last event came at 16:29:43Z, the worker kept heartbeating while the step fetched packages and images, and at 16:44:58Z Sortie cancelled the run as stalled; the agent then exited on taichi and the worker's report was refused because the lease was gone.

The adapters that track tool calls (`agent-client-protocol`, `claude-code`, `codex`, `copilot-cli`) now emit `domain.EventToolStarted` with the call's ID, and set the same `ToolCallID` on the `tool_result` that ends it. The orchestrator keeps each run's open calls in `RunningEntry.OpenToolCalls` (`trackToolCall` in `internal/orchestrator/event.go`; a turn's end clears them). `stallTimeout` in `internal/orchestrator/state.go` picks the bound for both the stall check (`reconcileStalled`) and the snapshot's `quiet_at` and `stall_at`: `agent.tool_call_timeout_ms` (default 90 minutes) while a call is open and `State.WorkerLive` reports the worker alive, else `agent.stall_timeout_ms`. Under the remote kind `WorkerLive` is `remoteWorkers.leaseCurrent`, whether the job's lease is unexpired, so a worker that stops heartbeating takes the 15-minute rule and its lease expires as before; under every other kind the worker is this process. Running rows serve `in_tool_call_since`. Hooks in upstream files: the event type and field in `internal/domain/agent.go`, the four adapters' tool-start sites, the config key, the two `State` fields set in `Run` and the poll tick, the stall check and the snapshot, the row field in `internal/server/handler.go`, and the `stall_marker_tool_call` sentence. A run adopted after a restart starts with no open call, so until its next tool call it is measured against `agent.stall_timeout_ms`.
