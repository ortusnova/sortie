# This fork

This repository is the agentic-orchestration fork of [Sortie](https://github.com/sortie-ai/sortie). Its working branch is `plan-bench`; agentic-orchestration pins it as the `sortie/` submodule.

## Merging upstream

- Merge upstream `main` into `plan-bench` at each upstream release, or weekly when no release comes, whichever is sooner.
- Merge, never rebase: open a `merge/upstream-<date>` branch from `plan-bench`, run `git merge upstream/main`, and land it through a pull request. Rebasing would rewrite commits that agentic-orchestration's submodule pins.
- Record in the merge commit body each conflict whose resolution changed the meaning of either side: the file, what each side did, and what was kept. Record the upstream commit merged, so the next merge knows where it starts.
- Keep fork work in fork-owned packages and files, with small hooks in upstream files, so each merge stays small. Fork database migrations are numbered from 1001 and fork ADRs from 1001, so upstream's numbers never collide with them.

Last merged upstream commit: `c48b724b` (2026-10-28).

## Worker leases

Jobs for `environment.kind: remote` are matched to workers in `internal/worker`, wired into the orchestrator in `internal/orchestrator/remote.go`, configured in `internal/config/environment_remote.go` and served by `internal/server/worker.go`, following the `agent-platform/worker-api` (protocol 1) and `agent-platform/worker-dispatch` specs. The lease rule sits behind the `worker.Leaser` interface. Until upstream #1499 settles, the fork follows a fixed-duration rule (`TTLLeaser`): one worker holds a job at a time, a lease lasts its TTL from the grant or last renewal, and an expired lease ends the attempt as failed; the worker's run slot, CPUs and memory return, and its disk stays counted as a stopped machine's until the worker's next check-in. Replacing the rule means implementing `Leaser`. Placement is `place` in `internal/worker/worker.go`, which both `Matcher.Poll` and `Matcher.Placeable` use: jobs fewer workers are capable of are placed first, and each job goes to the worker it fits with the fewest capabilities it does not need, then to the polling worker, so a scarce capability such as `nested` is spent only on the jobs that need it; a poll offers a worker only the jobs placed on it.

## Remote runs

A remote attempt is a normal worker run (`RunRemoteAttempt` in `internal/orchestrator/remote.go`, following `agent-platform/remote-runs`): the attempt's execution environment is the job's machine, Sortie drives the agent session over the `stdio` flow through `sortie stdio-bridge`, and seeds and pushes the repository through `internal/gitsync` (`BuildSeed`, `ImportReturned`). `internal/dataplane` serves the `stdio`, `mcp`, `bundles` and `usage` flows under `/api/v1/flows/`, each request admitted by its flow's job token. The remote attempt is a tool-channel environment whose host socket is the data plane's: the session's tool server is served there as for a VM, and the `mcp` flow forwards each admitted request to it with the bearer the channel's `Authorize` hook hands it, so a tool call acts on its own job's session. No forge credential reaches a worker. After each turn `RunWorkerAttempt` calls `remoteRepository.syncSortieFiles`, which asks a worker on `sortie-stdio/2` for the agent's `.sortie` files (`dataplane.Attempt.SortieFiles`, the `S` and `F` frames) and writes them into the host workspace, so the turn loop's status read and its criteria-verdict exit (`criteriaRecorded`) see the worker's files.

## Job egress policy

Each offer's run descriptor carries the job's egress policy as `run.egress`, following `agent-platform/job-egress-policy`; worker-daemon applies it and runs no job whose offer lacks it. `internal/egress` reads and checks the format, `.sortie/egress.yaml` in a repository and `environment.remote.egress` in the workflow (`parseRemoteEgress` in `internal/config/environment_remote.go`), and `docs/egress.schema.json` publishes it; the schema tests in `internal/egress` keep the two in step and validate every example of the workflow reference and this repository's own file. Sortie reads the file only at the base branch: `gitsync.Syncer.ReadBaseFile` fetches and reads at the tip of `base` for the dispatch check, and `remoteRepository.Seed` reads it with `gitsync.Syncer.FileAt` at the seed's `Seed.Base`, which the offer carries. An invalid file holds the issue with `egress_invalid` (`internal/orchestrator/egress.go`: `egressHold`, read once per repository per pass by `egressPass`, and `holdForEgress`, which comments once per hold and keeps `State.EgressHoldNoticed`). Hooks in upstream files: `SkipEgressInvalid` in `HoldReasons`, the check before `workerWait` in `handleTick`, `HandleRetryTimerParams.EgressHold` and `RetryEntry.EgressHold` in `HandleRetryTimer`, `HeldEntry.Egress` and `SnapshotHold.Egress`, the hold's `egress` and the retry's `egress_hold` in `internal/server/handler.go`, and the `hold_egress_invalid` sentence.

## A restart keeps the remote runs

A Sortie restart interrupts no remote run, following `agent-platform/run-supervision` ("A Sortie restart interrupts no run, and a deploy never drains"). From a worker's lease grant to the attempt's end, `internal/orchestrator/remote.go` keeps the run's record in `remote_runs` (migration 1011, `internal/persistence/remote_runs.go`): the job, the worker, the job tokens' digests (`jobtoken.Issuer.Digests`) and the seed at the grant (`worker.Matcher.Granted`), the agent session and its turns from the adapter wrapper, and the running entry (issue, dispatch, attempt, stage, reaction, budgets, broker) from the event loop. At shutdown the attempt is left with its worker: once the event loop's context ends, a recorded attempt never cancels its job, deletes its record or sends the `C` frame (`dataplane.Options.Keep`, `Attempt.Detach`), and its exit records nothing (`keepRemoteExit`). At start, `RestoreRemoteRuns` restores the leases (`worker.Matcher.Adopt`) and tokens (`jobtoken.Issuer.Restore`) before the server serves the worker API, and `adoptRemoteRuns` puts each run back in the running map with its dispatch ID and starts its worker with `RunRemoteAttempt`'s `Adopt`: the session resumes the recorded one and the turns continue after the completed ones (`WorkerDeps.Adopted`). The adopted entry's `AdoptedAt` (runtime-only) is the adoption time, and `stallReference` measures the run's silence from no earlier than it; the record keeps the last agent event (`last_event_at` in the stored entry, written with the entry at each turn's end and at shutdown) only for `last_event_at` on the running row. Before this, an adopted run was measured from its start, so every run older than `agent.stall_timeout_ms` was stopped as stalled on the first pass after a restart (seen on p1 on 2026-11-03: ONS-19, ONS-69 and ONS-109). An open tool call is not restored: worker-daemon stops the agent when the stream breaks, so the call ended with it. The code is in `internal/orchestrator/remote_adopt.go`. Hooks in upstream files: `WorkerDeps.Adopted` and its three checks in `RunWorkerAttempt` (no in-progress transition, no `session.started`, the turn counters and skip), the `keepRemoteExit` check in `handleWorkerExit` and `drainRunningWorkers`, `detachRemoteRuns` in `drainRunningWorkers`, `adoptRemoteRuns` in `Run`, the record after a broker report in `handleControl`, the store in `NewOrchestrator`, the two `RemoteAttemptParams` in `makeWorkerFn`, and `RestoreRemoteRuns` in `cmd/sortie/main.go`. The worker side is worker-daemon's: on a broken stream it keeps the job's machine, dials the `stdio` flow again and starts the agent again. A CI log excerpt is never stored, so a CI fix turn run again after a restart has an empty one.

A worker daemon's restart keeps the run too. When the worker breaks a recorded attempt's `stdio` stream before the agent's exit, `remoteAttempt.rehome` detaches the attempt as a shutdown does, keeps the job's outcome channel (`remoteWorkers.rehoming`) and cancels the run with `errRemoteRehome`; its exit is kept (`keepRemoteExit`), and `readoptRemoteRun` decodes the run's record (`decodeAdoption`) and adopts it again through `adoptRemoteRuns`, with the lease and tokens still live. Only an attempt with no record is still ended by `stallBrokenStream`. A restarted worker daemon keeps no job token at rest, so it takes the attempt's tokens again with `POST /api/v1/workers/jobs/{job}/attempts/{attempt}/resume` (`worker.Matcher.Resume`, which mints them anew); `remoteWorkers.resumed` writes their digests into the run's record (`UpdateRemoteRunRecord`) before the worker gets them, and refuses while the process stops. Seen live on p1 on 2026-11-03: each worker daemon deploy broke its jobs' streams, and Sortie cancelled ONS-20, ONS-72, ONS-97 and ONS-103 as stalled within seconds.

A job Sortie no longer wants is released, not kept. `worker.Matcher` keeps each job's last ended attempt and why (`endedJobs`), and a heartbeat or report for an ended attempt, or for one it does not hold, gets `worker.ErrJobGone`, which the worker API answers `410 job_gone`; on the data plane, `jobtoken.Issuer.Ended` knows the tokens of each job's last ended attempt, and `dataplane.Plane` answers them `410` instead of `401`. A restarted matcher is `Recovering` from `newRemoteWorkers` until `adoptRemoteRuns` calls `Recovered`, and meanwhile answers a job it does not know with `worker.ErrRecovering`, `503 recovering`, which the worker retries. An adopted attempt withdraws its job when it finishes even if it never reached `AfterCreate` (`remoteAttempt.finish`): seen live on p1 on 2026-11-03, ONS-19's adopted run was cancelled while it read the issue's description, its job stayed leased, and taichi's worker kept the machine and 60 GiB of disk, heartbeating and dialing the `stdio` flow, until a person stopped it. worker-daemon releases the job on `410`.

## Failure causes

A failed run keeps its whole cause in `run_history.error_detail` (migration 1005), served as `error_detail` on every run row, following `agent-platform/run-supervision`. `internal/failcause` reads it from the first error in the run error's chain that has a `FailureOutput() string` method, masks it and caps it; `gitsync.Error` (a git command's porcelain output and standard error) and the `agent-client-protocol` adapter's JSON-RPC error cause (the runtime's error object) have one. Another adapter adds a cause by giving its error that method.

A run that ends on an error also gets a failure signature in `run_history.failure_signature` (migration 1006), following the requirement "The same failure twice stops the retries" of `agent-platform/run-supervision`. `failcause.Sign` builds it from the failed step the orchestrator names, the class `failcause.Classify` gives the error, and the error's first line through `failcause.Normalize`. An error type names its own class with a `FailureClass() string` method, as `gitsync.Error` does (`git_<subcommand>`). When an issue's run fails with the signature of its previous run and the class is not transient, the exit parks the issue with the reason `repeated_failure` instead of scheduling a retry; the transient classes are listed in `failcause.TransientClasses`.

A repeated failure is then routed by its fault class, following the requirement "A stopped failure goes to whoever can act on it" of `agent-platform/run-supervision`. `failcause.RouteOf` matches the signature against `failcause.FaultClasses`, a fixed, ordered list of story and platform classes with the signature patterns in each and, for a platform fault only a person can clear, the action template. A story fault schedules one retry with the trigger `story_fault` whose first-turn prompt gets the failure section (`prompt.FailureHandOver`); its own repeat parks the issue with `repeated_failure`. A platform fault is recorded once in `platform_faults` (migration 1009, `internal/orchestrator/platform_fault.go`) and holds its stories in `State.FaultHolds`, which the dispatch gates and the retry timer respect. `internal/orchestrator/platform_fault_check.go` runs the checks: on the poll tick when due, every `PlatformFaultCheckInterval`, and at once from `POST /api/v1/platform-faults/{id}/action-done` (`internal/server/platform_fault.go`). The default check probes an `export` fault with `gitsync.Syncer.PushIncoming`, and otherwise passes a person-action fault once it is marked done. The workbench reads `platform_faults` on `/api/v1/state` and asks each `person_action` as a question naming its stories; marking the question done calls the action-done route. The host a person action names is the machine's host name.

## Health checks before runs fail on them

Sortie checks what its runs use before a run fails on it, following the requirement "Sortie checks its own health before runs fail on it" of `agent-platform/run-supervision`. `internal/orchestrator/platform_health.go` runs the checks on the poll tick every `HealthCheckInterval` and before a dispatch whose last check is older than a minute, in `handleTick`'s dispatch pass and through `HandleRetryTimerParams.HealthHold` for retries. A failing check records a platform fault of the step `health`, which the workbench asks as it asks any other; a credential, forge token or deploy fault holds the stories that would dispatch, and a passing check resolves the fault and releases them. The checks read the credentials `health.credentials` lists anew (the `env` variable, with the expiry from the entry's `expires_command` through `credsource.ReadExpiry`, or a JSON Web Token's `exp`), the SCM adapter's token through the optional `domain.SCMTokenInspector` (GitHub: `X-OAuth-Scopes` and `GitHub-Authentication-Token-Expiration` on `GET /rate_limit`; a change under `.github/workflows/` needs `workflow`), the paths a story's branch changes in the host mirror (`gitsync.Syncer.ChangedPaths`, which fetches nothing), the stage-0 kit's deploy state file `health.deploy_state` (`internal/deploystate`), and the worker matcher's check-ins under `remote`. A fault of the `health` step is checked again by `checkHealthFault`. Hooks in upstream files: the `runDueHealthChecks` and `healthHold` calls in `handleTick`, the `HealthHold` gate in `HandleRetryTimer`, the `health` step in `checkPlatformFault`, one line in `applyFaultCheckOnLoop`, the `health` section in `internal/config`, and one parameter in `cmd/sortie/main.go`.

## Plan sync from the workbench

The agentic-orchestration workbench syncs the plan on its own, with no Sync step for the user. It calls `POST /api/v1/plan/sync` with `"apply": false` to preview, then applies that preview with `"apply": true` and the preview's `preview_id`. After a sync that released a story, it calls `POST /api/v1/refresh` so the released story is dispatched on the next tick instead of the next poll. Both routes take the control token. Nothing else in Sortie changes for this.

## Draining a host

The stage-0 kit drains a host before a deploy or a host setup change, following `agent-platform/run-supervision` ("A pending deploy drains its host"). It calls `POST /api/v1/dispatch/pause`, waits until `running` on `/api/v1/state` is empty, applies the change, and calls `POST /api/v1/dispatch/resume`; both routes take the control token. The pause lives in `internal/orchestrator/dispatch_pause.go` and `internal/server/dispatch_pause.go`, with one hook in the poll tick's dispatch pass and one in `HandleRetryTimer`. It is kept in memory, so a restart clears it: the kit resumes after every change and repeats its pause each minute while it waits, so a persisted pause would add nothing and could leave a host paused with no one to resume it.

Under `environment.kind: remote` a restart keeps the runs its workers hold (see below), so a deploy of such a Sortie needs no drain.

## More sessions for one issue

The workbench unblocks a story the session budget holds, following `agent-platform/run-supervision` ("Unblock from the lane"). It calls `POST /api/v1/{identifier}/sessions` with `{"add": N, "by", "reason"}` and the control token, and the issue runs again without a change to `agent.max_sessions` for every issue. The grant lives in `internal/orchestrator/session_grant.go`, `internal/server/session_grant.go` and `internal/persistence/session_grants.go` (table `session_grants`, migration 1007). Hooks in upstream files count it: the poll tick's budget set in `rebuildBudgetExhausted`, the session gate in `HandleRetryTimer`, the snapshot, the served rows and sentences, and the `cost_budget` tool. Grants are stored, unlike the dispatch pause, because a story granted sessions must not be held again by a restart.

## The supervisor token

An agent supervises runs through a token of its own, following `agent-platform/run-supervision` ("The supervisor acts only through a scoped API, and each action is recorded"); blockers that need a person still go to a person. `server.supervisor_token` is accepted only on the routes of its actions: `answer`, `sessions` (capped by `server.supervisor_max_sessions`), and the fork's `unpark`, `merge-record`, `fix`, `draft`, `merge`, `merge-and-prove`, `live-proof` and `POST /api/v1/issues`. Hooks in upstream files: the two routes it shares with the operator, the cap on `SessionGrantRequest`, the `released` park gesture, the `supervisorView` member embedded in the state response and its `attachSupervisorActions` call, the `prDrafter` field, and the wiring in `cmd/sortie`. The draft capability is the optional `domain.PullRequestDrafter`, implemented by the GitHub adapter only. Sortie runs no live proof: a `live-proof` request is its stored record.

## Later turns of a reaction run

The fork changes the rule of upstream ADR 0037 for later turns. In `BuildReactionTurnPrompt` (`internal/prompt/reaction.go`), a turn after the first gets the operator's branch only when the branch renders differently with `.run.is_continuation` false; otherwise it gets the built-in continuation text, which also says that the earlier turns' commits are in the workspace and that `origin/<branch>` moves only after the run. Seen on 2026-11-02 and 03 in stage-0 fix runs (ONS-50, ONS-51, ONS-55, ONS-83): the fix template had no continuation branch, so each later turn asked again for the merge the agent had already committed, and the agent, seeing `origin/<branch>` unchanged because Sortie pushes after the run, parked to ask why Sortie did not push. The seed and refresh were correct: the next run's refresh moved `origin/<branch>` to the pushed commit.

## What each worker does

## smolvm egress with virtio-net

Answer: smolvm filters egress with `virtio-net`, and does not with TSI. Measured on smolvm 1.32.4 on 2026-11-01, on p1 (Intel, `kvm_intel nested=Y`), with throwaway Alpine 3.22 machines.

- **virtio-net filters.** A machine created with `--net-backend virtio-net --allow-host-pattern ghcr.io` reached `ghcr.io` (`HTTP/1.1 301`). `example.com` did not resolve (NXDOMAIN), `1.1.1.1` and `93.184.215.14` refused the connection, and `smolvm machine egress-events` recorded each refusal, including `github.com`, where the `ghcr.io` redirect points.
- **The default backend is the same.** Without `--net-backend`, a machine with an allowlist used the same virtio-net stack (`eth0`, resolver `100.96.0.1`) and showed the same results. So a workflow without `net_backend` keeps today's machines.
- **TSI does not filter.** smolvm refuses to create a machine with `--net-backend tsi` and any egress policy: "egress policy ... requires the virtio-net backend; TSI does not enforce it". A TSI machine has no `eth0` and uses the host's resolver.
- **A backend needs a network.** `--net-backend virtio-net` without an allowlist or a credential is refused: "--net-backend virtio-net requires --net". `--net` would open the network unfiltered.
- **Credentials need the allowlist.** A credential binding alone opens the network unfiltered, on every backend. With an allowlist that lacks the credential's host, smolvm refuses the machine. With the credential's host on the allowlist, which Sortie always adds, substitution works the same with virtio-net as without it.

The removed co-located `smolvm` kind followed these results: its `environment.smolvm.net_backend` accepted only `virtio-net`, refused `tsi` and every other value, and refused `virtio-net` without `allow_hosts` or `credentials`, and Sortie never added `--net`. The measurements stand for any worker that runs smolvm machines.

The same run measured the other host inputs. `--nested` gives the guest `/dev/kvm`, and `KVM_CREATE_VM` succeeds there; without it the guest has no `/dev/kvm`. `-v HOST:GUEST[:ro]` mounts over virtiofs: a read-only mount refuses every write, a link out of a mount does not reach the host, and smolvm accepts a mount under another one, such as under `/run/sortie/control`, so Sortie refuses that itself. A write to a mounted directory reaches the host at once, so it survives a `kill -9` of the machine, and `smolvm machine delete` leaves the directory alone.

## CI of a pull request in another repository

A workflow that dispatches several repositories (`dispatch.repositories`) has one CI provider, configured with one repository (`github.project`). Upstream's CI reaction read every pull request's CI from that repository, so a pull request in any other one got `422 No commit found for SHA` and its CI failure was never acted on. Seen live on p1 on 2026-11-03: `ortusnova/sortie#31` was read from `ortusnova/agentic-orchestration`. The providers now also implement `domain.RepositoryCIStatusProvider`, and the CI reaction reads each pull request's CI from the repository its reaction data names, with the same token (`internal/orchestrator/ci_reconcile.go`). The other pull request reactions already read the pull request's own repository through the SCM adapter.

## A queued reaction run across a restart

Upstream's merge-conflict reaction marked a conflicted head dispatched when it queued the rebase continuation, not when the run started. A queued continuation is runtime-only, so a restart loses it, and the mark kept the watch rebuilt at startup from dispatching that head again. Seen live on p1 on 2026-11-03: the merge-conflict reaction of `ortusnova/sortie#31` (ONS-78) queued its rebase at 04:05Z while every agent slot was busy, a deploy restarted Sortie at 08:12Z, and the pull request then stayed conflicted for hours with no rebase run. The fork drops that mark from `dispatchMergeConflictContinuation` (`internal/orchestrator/merge_conflict_reconcile.go`); `HandleRetryTimer` already marks the head when it starts the run, as it does for the `ci`, `review` and `bot-review` reactions. While the continuation waits, the retry-slot guard keeps the head from being queued twice. Persisting reaction retries instead was not chosen: their continuation context is not serializable as is, and the rest of the reaction state is rebuilt at startup, not stored.

Upstream's `label-review` and `label-fix` reactions likewise recorded a person's label command handled (the high-water mark, ADR-0015's at-most-once rule) and removed the command label when they queued the run, so a restart before the run started lost the command. The fork applies the same rule to them: the reconcile passes (`internal/orchestrator/label_review_reconcile.go`, `label_fix_reconcile.go`) queue the run with the command's mark and label on the retry entry (`RetryEntry.Command`), and `HandleRetryTimer` persists the mark and removes the label when it starts the run (`acknowledgeLabelCommand` in `retry.go`). While the run waits, the passes leave the mark alone, and the retry-slot guard keeps the command from being queued twice. A command whose run started is never repeated; a crash between the run starting and the mark write is the only window that can repeat one.

## The base branch in a remote run's workspace

Upstream's remote workspace seed bundled only `HEAD` and the issue branch. The worker daemon fetches every ref of the seed as it is (`+refs/*:refs/*`), so the workspace had no remote and no `origin/<base>`. Seen live on p1 on 2026-11-03: the merge-conflict runs of six stage-0 pull requests (ao#69, #79, #93 and sortie#51, #57, #58) each ran up to 20 turns of "there is no copy of `main` in this workspace to merge" and ended `succeeded` with nothing exported. `BuildSeed` (`internal/gitsync/seed.go`) now also bundles `refs/remotes/origin/<base>` and, when the upstream issue branch exists, `refs/remotes/origin/<issue branch>`, as a local workspace's refresh provides. `ImportReturned` now leases the push on the upstream commit the seed carried (`Seed.Upstream`) instead of on Sortie's last push: ONS-97's branch (ao#79) held a person's merge (`dbce406`) on top of Sortie's last push (`145162a`), so a returned merge on top of it would have been refused as `branch moved upstream`. A seed recorded before the upgrade has no `Upstream` and keeps the old lease.

## A rebase run that leaves the head unchanged

Upstream's merge-conflict reaction dispatched one rebase run per conflicting head. A run that ended with the head unchanged, because it could not merge, failed, or was lost to a restart after it started, left the head marked dispatched, and the pull request conflicted for good. Seen live on p1 on 2026-11-03: those pull requests, and ao#92 and ao#98, whose rebase runs a restart cancelled, stayed conflicting for hours after one run each, each with "0 of 1" attempts shown after a restart and no rebase run scheduled. The fork counts a head's dispatches in `reaction_fingerprints.dispatched` (`MarkReactionDispatched` adds one; the new `GetReactionDispatches` reads the count) and, in `handleMergeConflictDirty` (`internal/orchestrator/merge_conflict_reconcile.go`), gives a head still conflicting a poll interval after its runs ended, with no run of the issue running or queued, another run, up to `mergeConflictRunsPerHead` (3); then it escalates with the trigger `unresolved`. These runs spend no `max_retries` attempt, which keeps counting conflicting heads. A per-head bound in the store was chosen over the in-memory attempt counter, which a restart resets. A run that a shutdown cancelled or that failed in the fault class `worker_lost` gives its dispatch back at its exit (`returnLostMergeConflictDispatch` in `internal/orchestrator/exit.go`, `ReturnReactionDispatch` in the store), never below one: on 2026-11-03 one deploy, at 22:22Z, cut the rebase runs of ONS-70, ONS-72 and ONS-97 with `worker daemon shut down`. Refunding every failed run was not chosen, because a reaction continuation passes the park and platform-fault gates and could then loop.

## CI with a fine-grained GitHub token

A GitHub fine-grained personal access token cannot read check runs: GitHub offers it no Checks permission, and `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` answers `403`. Seen live on taichi on 2026-11-03, where every pull request waited on `ci_auth_error`. When that endpoint refuses the token, the GitHub CI provider and the auto-merge CI gate read the GitHub Actions jobs of the head commit instead (`internal/scm/github/ci_actions.go`): the workflow runs for the commit, the newest run of each workflow and event, its latest-attempt jobs, and the failing job's log. The refusal is kept per repository for an hour. The hooks in upstream files are one call to `readCheckRuns` in `FetchRepositoryCIStatus` (`ci.go`) and one in `GetCIStatus` (`merge.go`), plus a `refusals` field on each of the two types. The token needs Actions read-only access beside Contents, Pull requests, and Commit statuses.

## Work a session could not do

A build or review session records each part of its story it could not do in `.sortie/handoff.json`, following `agent-platform/run-supervision` ("Work an agent could not do is picked up, not left in the pull request"); the format is in the workflow reference. The worker reads the file at the end of a normal run into `WorkerResult.HandoffParts` (a remote worker returns it as the `handoff` part of the `bundles` result, `dataplane.Result.Handoff`), and `takeHandoffParts` records the parts after `HandleWorkerExit`. The code is in `internal/orchestrator/handoff_parts.go`, the table `handoff_parts` (migration 1015) in `internal/persistence/handoff_parts.go`, and the state view in `internal/server/handoff_parts.go`. A `job` part is queued on the worker matcher as a check job (`worker.JobKindCheck`, ID `handoff-<identifier>-<part>`) that requires the story's repository requirements plus the part's capabilities; a worker declares capabilities beyond its OS, architecture, KVM and backends in the optional `capabilities` of its check-in, and `worker.Matcher.Capable` says whether any live worker declares them. A `pull_request` part is filed through `domain.IssueCreator` with the `sortie-repository:` label of the named repository, and closes when that issue reaches a terminal state. A part nothing can carry is a platform fault with a person action, one per part, that holds the story; marking it done closes the part (`handoffFaultResolved`). Hooks in upstream files: the `HandoffParts` field and its read in `RunWorkerAttempt`, the `takeHandoffParts` call in `handleWorkerExit`, the `advanceHandoffParts` call in the poll tick, the `handoffFaultResolved` call in `applyFaultCheckOnLoop`, the open-part gates in `reconcileAutoMerge`, `processMergeCompletionEntry` and `completeMergedCandidates`, the `HandoffParts` maps of `State` and the snapshot, the `handoff_parts` member of the state response, and the load in `cmd/sortie/main.go`. The worker daemon runs a check job's command in the job's machine with no agent, seed or flows, and reports whether it exited zero.

## The co-located smolvm kind is gone

Following `agent-platform/one-sortie` ("The co-located mode and the second Sortie are gone"), the fork no longer offers `environment.kind: smolvm`, which ran each issue in a microVM on Sortie's own host. Once taichi ran as a worker, one Sortie on p1 dispatches every repository's jobs to workers under `remote`, so the kind, its package `internal/environment/smolvm`, the per-issue tool socket it mounted in each VM, its smolvm version check, the rule that excluded it from `worker.ssh_hosts`, the host machine listing behind `host.used` and `host.unmanaged`, and its guide were deleted. Validation refuses the kind with an error on `environment.kind` that names `smolvm` and `remote` (`internal/config/environment.go`), so a workflow left on it stops at start, and a reload keeps the previous one. The repository settings it shared with `remote` are `config.Repository` and `config.RepositorySet`. The generic environment hooks it used (`Carrier`, `ToolChanneler`, `EnvForwarder`, `Meta.CheckHost`, `Meta.SweepUnselected`) stay in `internal/environment` for the `remote` attempt and any later kind. A workspace the kind created records `smolvm` in `.sortie/environment`, which no registered kind builds any more, so its preparation and removal fail until its VM and directory are deleted by hand.

## A long tool call is not a stall

A run inside a tool call that is still in progress is not stalled while its worker shows the job alive. Upstream's stall check measures only the time since the last agent event, and a tool call emits none while it runs, so a long command ended at `agent.stall_timeout_ms`. Seen live on p1 on 2026-11-03: ONS-19 ran a seed step on taichi under `environment.kind: remote`, its last event came at 16:29:43Z, the worker kept heartbeating while the step fetched packages and images, and at 16:44:58Z Sortie cancelled the run as stalled; the agent then exited on taichi and the worker's report was refused because the lease was gone.

The adapters that track tool calls (`agent-client-protocol`, `claude-code`, `codex`, `copilot-cli`) now emit `domain.EventToolStarted` with the call's ID, and set the same `ToolCallID` on the `tool_result` that ends it. The orchestrator keeps each run's open calls in `RunningEntry.OpenToolCalls` (`trackToolCall` in `internal/orchestrator/event.go`; a turn's end clears them). `stallTimeout` in `internal/orchestrator/state.go` picks the bound for both the stall check (`reconcileStalled`) and the snapshot's `quiet_at` and `stall_at`: `agent.tool_call_timeout_ms` (default 90 minutes) while a call is open and `State.WorkerLive` reports the worker alive, else `agent.stall_timeout_ms`. Under the remote kind `WorkerLive` is `remoteWorkers.leaseCurrent`, whether the job's lease is unexpired, so a worker that stops heartbeating takes the 15-minute rule and its lease expires as before; under every other kind the worker is this process. Running rows serve `in_tool_call_since`. Hooks in upstream files: the event type and field in `internal/domain/agent.go`, the four adapters' tool-start sites, the config key, the two `State` fields set in `Run` and the poll tick, the stall check and the snapshot, the row field in `internal/server/handler.go`, and the `stall_marker_tool_call` sentence. A run adopted after a restart starts with no open call, since the restart stopped the agent that made it, so until its next tool call it is measured against `agent.stall_timeout_ms`, from its adoption (see "A restart keeps the remote runs").

## A parked story released by its pull request record

A parked story whose pull request holds, at its current head, the record its criteria verdict leaves open is released by that record with no new session, following `agent-platform/run-supervision` ("A UI is approved as a prototype, and the built story merges after its review", scenario "A record lands on a parked story", and "A live criterion a story's machine cannot run becomes a live-proof job"). Seen live on 2026-11-04 on ONS-97 (agentic-orchestration#79): the click-proofs on the preview parked the story, and their record was commented at the head more than three minutes before a person merged by hand, but Sortie never read it. Upstream reads the click-proofs record only inside `reconcileAutoMerge`, and a run that ends parked seeds no auto-merge entry; the supervisor's `merge` also refused every ui story.

`releaseParksByRecord` (`internal/orchestrator/park_record.go`), called from the poll tick, reads each parked story's pull request (`Supervisor.pullRequestOf`) at most once per auto-merge poll interval, under plan control with `tracker.handoff_state` and `reactions.auto_merge` set. `recordsNeeded` in `internal/orchestrator/plan_control.go` maps the latest criteria verdict to the records that settle it: `met` on a ui story needs `sortie:click-proofs passed <sha>`, `live-proof` needs `sortie:live-proof proven <sha>`, and `live-proof` on a ui story both; any other verdict, or none, is never released by a record. `recordsAtHead` finds each record naming the head (a prefix of at least 7 hex digits). A release moves the story to the handoff state, unparks it with the gesture `record` and its `ParkRecord` (pull request, head, comments), records a `handed_off` outcome naming them, and seeds the CI, merge-conflict, auto-merge and merge-completion watches at that head on the rule that carries `gate: criteria`, so auto-merge's normal checks decide the merge and failing CI or a conflict start their reactions. The review gate now lets a `live-proof` verdict through and marks the entry, and the record check (`ClickProofsFunc`) then also needs the live-proof record at the head; this applies to every auto-merge entry, not only a released park. The supervisor's `merge` merges a ui story whose pull request holds the click-proofs record at its head and refuses one without it with `click_proofs_missing`.

The release is kept on the park row (columns `release_pull_request`, `release_head`, `release_comment` of `parked_issues`, migration 1016) and served in `park_releases` on `GET /api/v1/state`; the latest record release of each story is kept in `park_record_releases` (same migration), and `Store.IssueOutcomes` returns it as `park_release` on the outcome while the outcome is of that pull request, so the merge still names it. The record checks are runtime-only, so a restart reads each park again on its first pass. Hooks in upstream files: the `releaseParksByRecord` call in `handleTick`, the `record` gesture in `isReleaseGesture`, the `Record` field of `ParkedEntry`, the `ParkReleases` member of the snapshot and the state response, the outcome columns read in `cmd/sortie/runhistory.go`, and the `missing` result of the click-proofs check in `reconcileAutoMerge`.

## Merge, prove after deploy, or revert

A story whose only unmet criteria are settled after deploy is merged, proven, or reverted by Sortie, following `agent-platform/supervisor-autonomy` ("A change provable only after deploy is merged, proven, or reverted by Sortie"). Seen on 2026-11-04: ONS-121 read Done although ao#144 had reverted ao#142, its merge, and its merge record still satisfied its dependents. A criteria check marks such a criterion `live-proof` with the reason `after-deploy` (`CriterionReasonAfterDeploy` in `internal/orchestrator/criteria_verdict.go`); `POST /api/v1/{identifier}/merge-and-prove` (`internal/server/supervisor.go`, `Supervisor.MergeAndProve` in `internal/orchestrator/merge_and_prove.go`) accepts the story only when the verdict leaves nothing else (`CriteriaVerdict.afterDeployCriteria`), its CI passed at its head and a ui story has its click-proofs there, and queues it. `advanceMergeAndProve`, on the poll tick, keeps one story in flight: `mergeStep` merges at the accepted head and drops the pull request's watches, `deployStep` reads each host's deploy state (`config.ServiceConfig.DeployHosts`: `merge_and_prove.hosts`, else `health.deploy_state`) and asks the forge whether its commit holds the merge commit (`domain.CommitComparer`), `proveStep` schedules a `live-proof` job against the deployed main (`scheduleAfterDeployProof`) and reads the pull request for `sortie:live-proof proven <sha>` or `sortie:live-proof unproven <sha>`, and `revertStep` opens the revert once (`domain.PullRequestReverter`, GitHub's `revertPullRequest` mutation) and merges it once its CI passes. A proven story gets its `merged` plan satisfaction only then, so its dependents wait for the proof; a reverted one goes back to `tracker.release_state` with the reason and publishes `story.reverted`. The queue and the story in flight are kept in `merge_and_prove` (migration 1017, `internal/persistence/merge_and_prove.go`), restored by `PopulateMergeAndProve` at startup, and served as `merge_and_prove` on `GET /api/v1/state` (`internal/server/merge_and_prove.go`). The live-proof job is runtime-only, so a restart in `proving` schedules it again.

A reverted story is not done, following "A reverted story is not done" of the same spec. `detectReverts` (`internal/orchestrator/story_revert.go`), on every poll tick, lists the merged pull requests of each repository with a merge record through the optional `domain.RevertFinder` (GitHub: the closed pull requests by update time, their body's `Reverts owner/repo#N` and their commits' `This reverts commit <sha>`), from the oldest record less seven days after a start and from the previous scan after that. A revert of a record's pull request or merge commit, whoever merged it, deletes the record (`Store.DeletePlanSatisfaction`, the only deletion of `plan_satisfaction`), so the plan judge blocks its dependents again, moves the story from a terminal or the handoff state to `tracker.release_state`, comments, and publishes `story.reverted`. Hooks in upstream files: the two calls in `handleTick`, the `mergeAndProveHolds` check in `processMergeCompletionEntry`, the three capabilities read in `NewOrchestrator`, the `MergeAndProve` and `RevertScans` fields of `State` and the snapshot, the state response member, the `story.reverted` event in `internal/domain/notify.go` and its body in `internal/notify/render`, the `merge_and_prove` section in `internal/config`, and the load in `cmd/sortie/main.go`.
